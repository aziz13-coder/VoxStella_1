## What The Current Models Actually Are

The current system is not machine-learned and it is not a recovered clone of the Almagest formulas.

It is an explicit weighted scoring engine built from:

- nearby natal angular lines
- nearby crossings / parans
- relocated-chart placements
- relocated-chart summary metrics
- optional transit overlay contributions

The scoring engine lives in:

- `backend/astrocartography_goal_engine.py`

The core grammar is:

- `line` component
- `crossing` component
- `relocation` component
- `modifier` component

Each model normalizes its raw total into a `0-100` score through a bounded linear range.

## Current Strengths

- The models are transparent and inspectable.
- Each model has explicit rationales for why a component is positive or negative.
- The goal families map well to the legacy Almagest category structure.
- The system is easy to extend without inventing another opaque file format.

## Current Limits

- The numeric weights are curated Vox Stella weights, not recovered legacy values.
- Most models still use one shared scoring grammar pattern with domain-specific weight swaps.
- Distance handling is still fairly uniform.
- The models do not yet use stronger conditional logic such as:
  - veto rules
  - hard incompatibilities
  - life-stage weighting
  - user intent subtypes
  - environment or practical filters

## What "More Advanced Models" Should Mean

The right next step is not to create dozens of shallow new goals. The right next step is to make the model layer more expressive.

### Advanced path A: split broad goals into specialist submodels

Examples:

- `career_executive`
- `career_public_profile`
- `work_remote`
- `work_stable_employment`
- `love_dating`
- `love_marriage`
- `home_family_nesting`
- `home_private_retreat`
- `money_business_growth`
- `money_asset_building`
- `education_research`
- `education_teaching`

This is the most product-useful next move because users often mean a subtype, not a broad domain label.

### Advanced path B: add conditional logic

Examples:

- if `uncertainty` is too high, cap score even when the line pattern looks promising
- if a model depends on partnership, require at least one supportive relationship-axis signal
- if malefic pressure is above a threshold, downgrade high-attraction but unstable romance results

This would make the models feel less "sum of weights" and more like actual decision profiles.

### Advanced path C: add domain overlays

Examples:

- `creative overlay`
- `family overlay`
- `stability overlay`
- `public visibility overlay`
- `spirituality overlay`

This would allow a user to search for:

- `Career + Stability`
- `Love + Marriage`
- `Home + Creativity`

That is likely more useful than a flat list of 20 independent goals.

### Advanced path D: add user-intent and life-stage tuning

Examples:

- early career
- mid-career advancement
- retirement / peaceful home base
- short-term romance
- long-term settlement
- study abroad
- entrepreneurial launch

This is where the product can go beyond the old legacy app rather than merely imitating it.

## Additional Sources That Would Help

If we want stronger source-grounded advanced models, the most useful extra sources would be:

- more Almagest PathFinder output samples
  - same natal chart
  - multiple goals
  - several returned cities
  - screenshots or exported reports
- any additional legacy profile folders
  - more `.PLS`
  - more `.HYP`
  - any docs describing model semantics
- more domain-specific astrocartography texts
  - relocation and vocation
  - relationships and marriage
  - home / family settlement
  - spiritual retreat / pilgrimage

The most valuable single source would be a larger observed I/O set from the original app. That would let us compare:

- which goals separate strongly
- which cities recur across domains
- whether the legacy app used hard gates or just weighted accumulation

## Recommended Product Direction

Do not build dozens of shallow goals next.

Build:

1. three remaining legacy-family models:
   - `personal_growth`
   - `communication`
   - `conflict`
2. one new advanced grammar layer:
   - conditional caps / vetoes
   - domain overlays
   - subtype models
3. then add specialist submodels in the areas users will actually ask for:
   - career
   - money
   - love
   - home

## Bottom Line

Yes, we can create more advanced models now.

But the best advanced move is not "more labels." It is:

- more expressive scoring logic
- better domain specialization
- stronger source comparison against observed legacy outputs

If more sources become available, the priority should be:

1. legacy app outputs
2. extra hidden rule files
3. domain-specific relocation texts
